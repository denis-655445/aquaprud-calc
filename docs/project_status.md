## 1. Мета та обмеження

**Мета:** майстер на об'єкті (iPhone) вводить габарити ставка → миттєво бачить рекомендоване обладнання та суму → зберігає кошторис у CRM і отримує його в чат Telegram.

**Обмеження:**
- Лише безкоштовні інструменти.
- ~20 клієнтів/міс; користувачі: власник-майстер (1) + технічний працівник (1).
- Залізо: MacBook Pro 2014 (Big Sur, 8 ГБ) — робоче місце через браузер; iPhone 11 — бойове використання і тести; Lenovo 110 — кандидат у домашній Linux-сервер для треку B.
- Власного сервера немає. Oracle Cloud — лише за наявності **легального** акаунта (§15).
- Технічний працівник — початківець: пропонуємо професійні рішення, вибір реалізації — за ним.

| D66 | Прибране «−» Bio лишається в `inputs.bios` (кеш, як D53): «+» повертає ту саму ширину й сторону (сторону зайняли — перша вільна за годинниковою); перемикач «вимк. / увімк.» повертає всі Bio одразу; «Новий кошторис» кеш скидає | п. 1.5 правок | видаляти дані |

## 6. Розрахунковий рушій (`core/calc.js`, чисті функції без DOM і без API платформ)

### 6.1 Вхідні поля (UI)

**Блок 1 — параметри ставка:** форма (прямокутний / овальний / нестандартний); L, W, D (м); риба (без риби / з рибою); біоплато (так/ні) + кількість 1–4 → для кожного Bio-N ширина і сторона (довжина = сторона ставка, D65); плівка (список `film`); відстань до фільтра, м; висота підйому води, м (за замовчуванням `lift_height_default_m`).

**Блок 2 — обладнання (автопідбір, редагується):** рекомендований потік і потрібний напір (інфо); фільтр; насос (рядок «у комплекті» або рекомендований окремий); УФ; скіммери (к-сть); донні (к-сть).

**Блок 3 — декор:** водоспад, світло (модель + к-сть), інше.

**Низ екрана:** дані клієнта (ім'я, телефон, адреса), коментар, живий підсумок, кнопка «Зберегти й надіслати».

**Службова панель (`SettingsButton`, меню «⋮»):** роботи % (±), націнка %, перемикач «приховати ціни», Про-режим, укіс у градусах (D67), біоплато на схемі «Разом / Окремо», розмір тексту, тема (D68). *Перевірити на iPhone; резерв — довге натискання на заголовок.*

### 6.2 Метрики

| Метрика | Формула | Статус |
|---|---|---|
| S | прямок.: L·W; овал: `shape_k_oval`·L·W; нестанд.: `shape_k_custom`·L·W | математика + налаштування |
| P | прямок.: 2(L+W); овал: π[3(a+b) − √((3a+b)(a+3b))], a=L/2, b=W/2 (Рамануджан) | математика |
| V | V₀ − C: V₀ = S_глиб·D + Σ S_vis·h, C — зрізане укосом 1 : m (D63) — `docs/stairs_math.md` §10.1 | укіс — службова панель |
| V_б | S_б · `bio_depth_m`, S_б = Σ len·w + Σ стиків w₁·w₂ (D65) | налаштування |
| V_заг | V + V_б | — |
| film_area | (L + 2D + 2·`film_margin_m`) · (W + 2D + 2·`film_margin_m`) | стандартний розкрій |
| bio_film_area | Σ по Bio: (filmLen + 2·`bio_depth_m` + 2·запас) · (w + 2·`bio_depth_m` + 2·запас); filmLen = len + ширини сусідів, чий стик приєднано до цього Bio (менший номер) | D65 |
| N_скіммерів | max(1, ⌈S / `area_per_skimmer_m2`⌉) | налаштування |
| N_донних | S < `drain_min_area_m2` ? 0 : ⌈S / `area_per_drain_m2`⌉ | налаштування |
| N_ліній | N_скіммерів + N_донних + 1 | **заглушка, уточнити** |
| pipe_len | N_ліній · (відстань + `pipe_reserve_m`) | **заглушка, уточнити** |
| excavation | V_заг · `excavation_k` | налаштування |
| Q_потр | V_заг · turnover(риба) · 1000, л/год | налаштування |
| L_напірна | 2 · відстань (туди й назад) | **заглушка, уточнити** |
| H_потр | висота_підйому + L_напірна·`head_loss_per_m` + `elbows_on_pressure_line`·`head_loss_per_elbow` + `filter_head_loss_m` | модель за пропозицією майстра |

### 6.3 Ключі «бази» для автопозицій

`pond_area`, `perimeter`, `volume`, `film_area`, `bio_film_area`, `film_area_total` (ставок + біоплато), `pipe_len`, `excavation`, `per_skimmer`, `per_drain`, `per_line`, `fixed`.
Автопозиції — лише категорії `geotextile`, `pipe`, `fitting`, `work` з заповненою базою; плівка береться з вибору в блоці 1 на площу `film_area_total`.
Кількість = метрика × `коеф`; округлення вгору для `шт`, до 0.1 для м/м²/м³.

### 6.4 Правила автопідбору

- **Фільтр / УФ:** найдешевша активна позиція з `макс_V_(з|без)_риби` ≥ V_заг.
- **Насос:** потік насоса при потрібному напорі — лінійне наближення Q(H) = Q_max · (1 − H/H_max). *Спрощення: реальна крива нелінійна; за потреби додамо 2–3 точки з паспорта.*
  1. Якщо у фільтра є `насос_комплект` і Q(H_потр) ≥ Q_потр → рядок «Насос: у комплекті» (0 грн).
  2. Інакше → найдешевший активний насос з Q(H_потр) ≥ Q_потр, **жирним**, з приміткою «насос комплекту недостатній».
  3. Якщо жоден не підходить → попередження в UI.
- Рекомендоване виділяється **жирним** і підставляється, поки поле не змінено вручну; «↺» повертає рекомендацію.

### 6.4a Схема ставка 2D / 3D (`core/pondgeo.js`, `miniapp/js/sketch3d.js`)

- План: x — вправо (L), y — вниз (W), z — вгору (земля 0, дно −D), як у `docs/stairs_math.md` §0.2.
- Контури: прямокутник; овал — 96 відрізків; «нестандартний» — умовно, прямокутник із заокругленими кутами (r = 0,38·min(L, W)).
- Біоплато (v0.7.1, D65) — `PondGeo.bioGeometry(shape, L, W, plates, joined)` → `rects` (Bio-N), `corners` (стики); «Окремо» — `pits` (проміжок max(0,5 м; 0,06·L), суміжні — один котлован, 4 Bio — кільце з діркою: `pit.holes`); «Разом» — `union`, `zones` (мілкі зони, у кільці — з діркою), `seams` (ламані шва). Глибина `bio_depth_m` з «Налаштувань». Підписи: 2D — «Bio-N» усередині Bio (вузьке — дрібніше / лише номер), 3D — біля зовнішньої сторони кожного Bio (D59 для кожного підпису).
- Проєкція: X = x·r₀ + y·r₁; Y = (x·c₀ + y·c₁)·sin α − z·cos α, де c — напрямок до глядача, r = (c₁, −c₀), α = 40°.
- Видимість точки: промінь до глядача піднімається на tan α на 1 м; межі ділянок ділять його на відрізки зі сталою висотою; точку заступає, якщо поверхня на початку відрізка вища за промінь. Сходинки — ті самі ділянки (`levels`), код уже враховує їх (тест).
- Заливки коректні для ставка без сходинок (отвір котлована обрізає дно); зі сходинками — доопрацювати на A2.1.
- Масштаб (v0.6.3): 3D — масштаб і горизонталь спільні для 4 ракурсів, висота блока однакова (D58), підпис «біоплато» — D59; 2D — `UI.fitPlan` (D60), hMax 2D = 0,6 ширини (портрет). Історія: (v0.4.1, D50) SVG у px блока; масштаб однаковий для 4 ракурсів — найбільший, за якого силует креслення не заходить під кнопки й підписи поверх схеми (бінарний пошук); у портреті висота ≤ min(ширина, 0,62·висоти екрана), в альбомі — висота екрана − 24 px. Під час повороту — той самий масштаб (кешується), крок перевірки видимості грубіший (3 px).
- Сходинки в 3D (v0.5.0, D49): `levels` у сцені — многокутники з дірками в координатах плану (`Stairs.toPlan`); вздовж стінки точки не спрощуються, внутрішній край — Дуглас — Пекер; поверхні рівнів заливаються від глибокої до мілкої.
- Біоплато «Разом» (v0.6.1, D56): `PondGeo.bioJoin(shape, L, W, bio, side)` → `{ rect, union, zone, seam }`; сцена — один котлован з контуром `union`, біоплато — рівень `zone` (`bio: true`), `seamWall` — контур ставка (на шві ребер немає), `floorOutline` — де справді дно. Сцена повертає `bio` (ділянка для підпису) і `pondOutline`. Інваріант (тест): площа `union` = площа ставка + площа `zone`.

### 6.5 Сходинки (Про-режим)

Повна математика, правила будівництва ставків, перевірки й приклади — `docs/stairs_math.md`. Коротко: шари «Полиця» / «Платформа», край «Прямі» (ламана) / «Округлі» (одна дуга через E_A, M′, E_B), ширини w_c / w_e, глибини 20 / 45 / 60 см, видимі площі з урахуванням перекриття, V по зонах.

### 6.6 Підсумок

Σ Обладнання, Σ Матеріали → Роботи = `labor_pct`% × база (`labor_base`) + ручні позиції `work` → × (1 + `markup_pct`/100) → Разом. Режим «приховати ціни» ховає суми на екрані, але не впливає на збережений кошторис.

## 7. API-контракт (платформонезалежний)

Mini App знає лише `API_BASE` (`miniapp/js/config.js`). Переїзд на сервер = зміна одного рядка.

**GET** `{API_BASE}?action=ping` → `{ ok: true, api }` (без доступу до даних — перевірка адреси)

**GET** `{API_BASE}?action=catalog&initData=…` → `{ ok: true, version, is_test, settings: {...}, items: [...], warnings: [...] }` (v0.8.0; помилка доступу — `{ ok: false, error: "auth", message }` з причиною, D71)

**GET** `{API_BASE}?action=estimate&number=AP-2026-001&initData=…` → `{ ok: true, estimate }` — збережений запит (v0.9.0)

**POST** `{API_BASE}`, `Content-Type: text/plain` (без CORS preflight), тіло — JSON (v0.9.0):
```
{ action: "saveEstimate", initData, payload: estimate }
estimate = {
  uid,                                   // ідентифікатор кошторису в телефоні (D77)
  summary: { client, phone, address, shape, dims, area, volume, bio, film, filter, uv, pump, head,
             skimmers, drains, steps, equipment, materials, labor_pct, work, total, comment, app_version },  // колонки CRM
  client:  { name, phone, phoneCountry, address },
  inputs:  { shape, L, W, D, fish, bio, bios: [ { side, w } ], filmId, distance, lift, slope_deg, slope_m, steps: [...] },
  lines:   [ { id, name, unit, qty, price, sum, group } ],
  totals:  { equipment, materials, work, labor_pct, labor, markup_pct, markup, subtotal, total },
  comment, clientComment, text,          // text — кошторис для клієнта без номера (номер — у заголовку повідомлення)
  app_version, catalog_version,
  app_state: { state, svc }              // стан застосунку — для «Відкрити в калькуляторі»
}
→ { ok: true, number: "AP-2026-001", created: true | false, notified: 2 }
```

**Службові дії (трек B, read-only):** `{ action: "listEstimates", apiKey, payload: { status?, days? } }` — ключ `SERVICE_API_KEY`, лише читання.

**Помилки:** завжди HTTP 200, `{ ok: false, error: "auth" | "validation" | "internal", message }`.

## 8. Безпека

1. **`initData`** — HMAC-SHA256 за алгоритмом Telegram; відхиляємо, якщо `auth_date` > 24 год або `user.id` ∉ `ALLOWED_USER_IDS`.
2. **Секрети** — лише в Script Properties / Worker Secrets / `.env` на сервері. У репозиторії — ніколи.
3. **Google-акаунт** — 2FA обов'язкова (персональні дані клієнтів).
4. **ШІ** — лише технічні параметри, без ПІБ і телефонів.
5. **Сервер (якщо буде):** вхід лише за SSH-ключем, автооновлення безпеки, закритий фаєрвол; бот — long polling (вхідні порти не потрібні).
6. **Hermes (трек B):** окремий токен; Docker-ізоляція; allowlist лише наших Telegram ID; без `BOT_TOKEN` основного бота і без прав запису в таблицю; доступ до даних — лише через read-only API.
7. **Довіра до розрахунку клієнта:** сервер не перераховує суми (користувачі свої). Якщо з'являться сторонні користувачі — серверна валідація через те саме `core/`.

8. «Приховати ціни» — так.
9. (v0.8) Глибина біоплато — стандартна, з «Налаштувань» (`bio_depth_m`), у полях не вводиться.

## 12. Переносимість (як не переписувати код при переїзді)

1. **Одна мова — JavaScript** всюди: браузер, Apps Script (V8), Cloudflare Worker, Node.js.
2. **Ядро без платформних API.** Apps Script не підтримує `import/export`, тому модулі ядра — «універсальні»: глобальна змінна + умовний експорт для Node:
   `var Calc = (function(){ ... return {...}; })(); if (typeof module !== 'undefined' && module.exports) module.exports = Calc;`
3. **Порти:**

| Порт | MVP-адаптер | Серверний адаптер |
|---|---|---|
| Storage | `SpreadsheetApp` | Google Sheets API (service account) — таблиця лишається адмінкою |
| Messenger | `UrlFetchApp` → Bot API | `fetch` → Bot API |
| Crypto (HMAC) | `Utilities.computeHmacSha256Signature` | `node:crypto` |
| Secrets | Script Properties | `.env` / Docker secrets |
| Updates бота | webhook (Worker) | long polling |
| LLM / STT | Gemini / Groq з Worker | Gemini / Groq або Hermes API |

4. **Контрактні тести:** ті самі `tests/fixtures/*.json` проганяються в браузері (`tests.html`) і в Node → однаковий результат на всіх платформах.
5. **Одне джерело оновлень бота:** або webhook, або polling — не одночасно.

## 13. Тригери переїзду на сервер і runbook

**Тригери (достатньо одного):** потрібен агент 24/7 (Hermes); складні PDF / обробка фото / фонові задачі; кілька майстрів і серверна валідація; стабільні затримки Apps Script, що заважають роботі.

**Runbook (API і чат):**
1. Хост за B0, Docker, `.env` з тими самими назвами секретів.
2. Розгорнути `adapters/node`; прогнати фікстури проти нового `API_BASE`.
3. HTTPS для API (субдомен `aquaprud.com` через Cloudflare Tunnel або Caddy) — потрібен, бо Mini App звертається з браузера.
4. Змінити `API_BASE` у `config.js`, підняти `?v=`.
5. Бот: `deleteWebhook` → запустити polling на сервері.
6. **Відкат:** повернути `API_BASE` на Apps Script `/exec`, `setWebhook` на Worker. Старі деплойменти не видаляти.

## 14. Hermes Agent — стратегія (трек B)

- Роль: особистий асистент власника/техпрацівника, **не** клієнтський і **не** в ланцюжку розрахунку.
- Хост: легальний Oracle / Lenovo з Linux / VPS. Для шлюзу Hermes потужності достатньо; модель — зовнішня.
- Модель: документація Hermes рекомендує платний Gemini для агентних сесій — free-квоти вистачає на кілька агентних ходів. Рішення про невеликий платний ключ — поза поточним обмеженням «лише безкоштовно»; ухвалюємо на старті B1.
- Сценарії: дайджест кошторисів без відповіді; нагадування; чернетки повідомлень клієнтам; пошук паспортних даних обладнання для прайсу.
- Інтеграція з ядром: лише read-only API (§7). Пізніше — можливий виклик Hermes як LLM через його OpenAI-сумісний API (порт LLM), з Gemini як резервом.

## 15. Oracle Cloud — оцінка

- Always Free (2026): Arm A1 — 2 OCPU / 12 ГБ сумарно (ліміт урізано вдвічі у 2026 без анонсу) + 2 AMD micro.
- Ризики: вилучення «простою» (7 днів, p95 CPU < 20%) — наш профіль навантаження; «out of host capacity»; адміністрування на нас.
- Правила: один акаунт на людину; дані й картка — достовірні, з згодою власника; віртуальні/передплачені картки не приймаються. Акаунт на чужі дані для обходу бану — **не використовуємо** (ризик раптового закриття; юридично власник інфраструктури — інша особа).
- Легальний шлях: звернення в підтримку Oracle щодо помилки з віртуальною карткою.
- Вердикт: ядро — 3/10; лабораторія для треку B при легальному акаунті — 6/10.
- Рішення - поки не використовуємо.

## 16. Ризики

| Ризик | Вплив | Захід |
|---|---|---|
| Токен бота у файлі проєкту | повний контроль над ботом | `/revoke`; лише в сховищах секретів |
| Секрет у публічному репозиторії | компрометація | секрети ніколи не в коді; перевірка перед комітом |
| Зміна free-лімітів Gemini / Groq / Cloudflare | ШІ-модуль зупиняється | ядро A1–A4 від ШІ не залежить; порт LLM дозволяє заміну |
| Закриття серверного акаунта (Oracle тощо) | зупинка треку B / серверного API | стан лише в таблиці (D12); відкат на serverless (§13) |
| Відключення світла (домашній сервер Lenovo) | асистент недоступний | трек B некритичний; ядро serverless |
| Hermes виконує небажані дії | доступ до даних / сервера | Docker, allowlist, без секретів ядра, read-only API |
| Ручне пошкодження таблиці | збій каталогу | перевірка даних у колонках; валідація каталогу |
| Кешування Mini App | стара версія | `?v=N` |
| Слабкий інтернет на об'єкті | неможливо зберегти | кеш каталогу; офлайн-черга (A7) |
